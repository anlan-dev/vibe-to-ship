# 阻塞点手册

> 在 vibe-to-ship 的 5 个阶段中，每个阶段都有可能卡住。
> 本文档是"卡住时翻这本"的速查手册，覆盖最常见的卡顿场景和应对方案。

**如何使用**：找到你当前卡住的那个场景 → 按照诊断树推进 → 如果还不行，最后有"终极退路"。

---

## 阶段 1 卡顿：需求不清

### 场景：创始人说不清自己要做什么

**诊断树**：
```
1. 给填空模板：
   "我是____，我经常遇到____的问题，
    现有的解决方案____不够好因为____，
    我希望有一个工具能____。"

2. 如果需要更多启发，挨个问：
   - 这个问题让你最烦的是什么时刻？
   - 你上次遇到这个问题是什么时候？
   - 你当时是怎么解决的（哪怕很笨）？
   - 如果有个魔法按钮能一键解决，你希望它做什么？

3. 如果还填不出来：
   → 建议创始人找 3 个有同样问题的人聊 5 分钟
   → 回来再回答第 1 步的填空
```

### 场景：创始人想做的功能太多（> 8 项）

**诊断树**：
```
1. 追问："如果只能上线一个功能，哪个最重要？为什么？"
2. 用 MoSCoW 框架：
   - Must have（必须有，否则产品没意义）→ 上限 3 项
   - Should have（应该有，但第一批可以没有）
   - Could have（可以有，以后再说）
   - Won't have（明确不做）
3. Must have 以外的全部移到 "vNext" 栏
4. 如果创始人仍然坚持 → 问："我们能不能先做 Must have，3 天上
   线，然后根据反馈决定第二批做什么？"
```

### 场景：创始人反复改方向

**诊断树**：
```
1. 温和提醒："这是 MVP 验证，不是最终产品。做出来比做完美重要。"
2. 如果创始人焦虑 → "是不是看到竞品做了什么让你慌了？我们聊聊。"
3. 终极方案："我们先固定一个方向做 3 天，3 天后你试用。如果方向
   不对，我们有 git 记录，核心模块可以复用。"
```

## 阶段 2 卡顿：视觉方向模糊

### 场景：创始人选不出视觉风格

**诊断树**：
```
1. 给 3 个默认推荐包：
   A. 极简白 + 蓝色强调 — 适合工具/SaaS/效率产品
   B. 暗色主题 + 渐变紫 — 适合创意/个人品牌/AI 产品
   C. 温暖米色 + 大圆角卡片 — 适合生活/习惯/健康产品

2. 如果创始人说"都不太对"→ 让创始人找一张图（任何来源），说出
   这张图里他喜欢和不喜欢的分别是什么。

3. 如果选不出来 → 默认方案 A，承诺后续可调（换 CSS 变量即可）
```

### 场景：参考图找了一大堆但互相矛盾

**诊断树**：
```
1. 帮创始人提炼："从这几张图里，我看到你喜欢 __ 和 __ 的质感，
   但不想要 __ 的复杂度和 __ 的配色。对吗？"
2. 如果提炼失败 → 让创始人只留 1 张最喜欢的图，其他全部删掉。
   从这一张图出发。
```

## 阶段 3 卡顿：文档写不下去

### 场景：创始人觉得"写文档浪费时间"

**诊断树**：
```
1. 明说风险："跳过 SDD 文档，最大的风险不是写不出代码，而是 3 
   天后你做出来的东西和你想象的不一样。而且你没法 pinpoint 是哪
   里出了问题，因为没有基线。"
2. 折中方案：只写一份精简 PRD.md（一页纸），DESIGN 和 
   ARCHITECTURE 边做边补。
3. 如果创始人坚持跳过 → 尊重，但声明："后续任何新需求出现时，
   必须先补上对应文档才能继续开发。"
```

### 场景：三份文档互相矛盾

**诊断树**：
```
1. 让 AI 把矛盾点列出：
   - PRD 说需要登录 → ARCHITECTURE 没写 auth 方案 → 矛盾
   - DESIGN 说暗色主题 → PRD 的用户旅程没考虑暗色场景 → 矛盾
2. 让创始人逐条决定以哪个为准
3. AI 修改其他文档以保持一致
```

### 场景：创始人审批文档时说不清"哪里不对"

**诊断树**：
```
1. 逐节确认："PRD 的定位部分 — 可以吗？功能清单 — 可以吗？"
2. 找到具体不满意的章节后，追问："是漏了什么，还是多了什么，还
   是描述不准确？"
3. 让 AI 给 2-3 个修改后的版本，创始人选一个方向
```

## 阶段 4 卡顿：开发跑不通

### 场景：AI 写出来的代码报错，修不好

**诊断树**：
```
1. 把完整报错信息贴给 AI，让它自己分析
2. 如果 3 轮对话后仍失败 → git reset --hard
3. 分析失败原因：
   - 技术选型问题？→ 回阶段 3 调整 ARCHITECTURE.md
   - 需求描述不清楚？→ 回阶段 3 补充 PRD.md
   - 代码写得不对？→ 换个角度重新描述需求给 AI
4. 重试该任务
```

### 场景：功能越做越多，MVP 膨胀

**诊断树**：
```
1. "好的，这个新需求很好。我们先更新 PRD.md 看看它在 MVP 范围内
   吗？"
2. 对照阶段 1 写下的黑名单 → 如果在黑名单里，温和地提醒创始人
3. 如果不在黑名单 → 加入 TODO.md 末尾，不阻塞当前进度
4. 如果创始人坚持要先做新需求 → 承认范围已变，更新 PRD 的 MVP 
   清单和优先级
```

### 场景：做完后发现 UI 和预想完全不一样

**诊断树**：
```
1. 打开 DESIGN.md，逐条对照：
   - 颜色对了吗？
   - 组件风格对了吗？
   - 状态视觉对了吗？
2. 如果 DESIGN.md 写得太模糊（比如只写了"好看"）→ 更新 
   DESIGN.md，补充具体数值（颜色代码、padding 值等）
3. 让 AI 逐组件重新实现，每一轮只调一个组件
```

## 阶段 5 卡顿：部署失败

### 场景：部署到 Vercel/Netlify 构建失败

**诊断树**：
```
1. 把构建日志贴给 AI
2. 常见原因和修复：
   - 构建命令错误 → 检查 package.json 的 build script
   - 依赖缺失 → 检查 package.json，npm install 后重试
   - Node 版本不匹配 → 在平台设置里指定版本
   - 环境变量缺失 → 检查 .env.example，在平台 dashboard 里配置
   - 文件路径大小写问题 → macOS 本地不区分但 Linux CI 区分
```

### 场景：部署成功但页面白屏

**诊断树**：
```
1. 打开浏览器开发者工具 → Console 看报错
2. 常见原因：
   - 路由配置问题（SPA 需要配置 fallback 到 index.html）
   - 环境变量缺失导致 API 调用失败
   - 静态资源路径错误（检查 base path 配置）
3. 把 Console 报错贴给 AI
```

### 场景：上线后发现 bug

**诊断树**：
```
分类：
├── 紧急（核心功能不可用）
│   → 立即修，走阶段 4 的"单任务流程"
│   → 修完重新部署
├── 非紧急（不影响核心功能）
│   → 记录到 TODO.md 的 "v1.1" 部分
│   → 不阻塞当前上线
│   → 下一批迭代统一修
└── 不确定
    → 问自己："这个 bug 会让第一批用户放弃这个产品吗？"
    → 会 → 按紧急处理
    → 不会 → 按非紧急处理
```

---

## 终极退路：全部推倒重来

如果以上诊断树都走不通，或者创始人觉得"方向彻底错了"：

1. **保留 docs/ 文件夹**（PRD、DESIGN、ARCHITECTURE 的知识还在）
2. **保留 git 历史**（不是没价值的，至少知道了"不能怎么做"）
3. **重新从阶段 1 开始**，但这次有上一次的经验教训
4. 新的阶段 1 核心问题是："上次哪里出了问题？这次怎么避免？"

---

## 记住

- 卡住是正常的，MVP 探索过程就是会遇到不确定
- 诊断树的目的不是"帮你做决定"，而是"给你可操作的下一个动作"
- 如果所有分支都走完了还是卡住 → 找用过 vibe-to-ship 的人聊一下，或者休息一天再回来看
